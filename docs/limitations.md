# Known limitations — 0.1.0-draft

This is a working draft of an agent-guided audit system, not an autonomous proof of correctness. The engine proposes scenarios from a bounded inventory and executes configured acceptance assertions; it does not synthesize and validate a complete suite for an arbitrary application without the host agent's reasoning.

- Exactly 101 areas are catalogued. Most require application-specific tests, source tracing or external infrastructure. A passed area only summarizes its configured cases. Excluded areas need credible scope reasons.
- Discovery is a keyword/source-module heuristic, capped at 3000 readable files, 20 MB total, 256 KB per file and 500 feature candidates. Oversized files/caps make readiness incomplete. Features not visible in the inspected artifacts can be missed; requirements must be reconciled by the host agent.
- Source fingerprints cover the inspected source/documentation and external harness sources, not Git history, ignored files, binary assets, deployment state or the entire build supply chain. Do not treat them as release attestations. Native/binary-only applications need additional evidence.
- Source inspection is not an OS sandbox. It skips symlinks and checks canonical boundaries, but is not designed for an attacker concurrently replacing filesystem ancestors during inspection. Use a stable owned checkout/disposable copy. Dynamic execution uses the separately described OS/container controls.
- Known credential files, dependencies, history, generated builds and symlinks are omitted. This reduces credential exposure but means scans do not establish that those omitted surfaces are clean. Bundle/history secret review remains a separate explicit gap.
- Automatic redaction cannot recognize every secret, personal datum or business-sensitive detail. Review outputs before sharing. Private report permissions are best-effort on platforms without POSIX permissions. Harnesses can still read sensitive values embedded in ordinary source files; use synthetic data and remove production credentials first.
- Source warnings are hypotheses. There is no machine false-positive disposition API yet. Evidence-backed agent triage can explain a false positive, but the conservative machine gate still fails on a high/critical warning. Do not change application behavior to hide a warning.
- The corrected fixture passes only 14 small assertions. It does not prove cryptographic strength, restart durability, concurrent charges, two-user chat, complete journeys, provider availability or production readiness. Add positive, boundary, concurrency and end-to-end controls for real apps.
- No real WhatsApp, email, SMS, push or payment connection is made. Provider contracts may change and simulations can drift. Actual delivery remains unverified; provider simulation success never becomes a production-delivery claim.
- macOS execution was tested locally. Linux/Windows/Docker, physical devices and actual scanner/browser executions were not available for end-to-end validation. Parsers and CLI/MCP contracts were tested. Docker/node restrictions may prevent an existing native/browser suite from running; that is blocked, not passed.
- macOS limits the JS heap, process lifetime and filesystem/network access, not all native memory or kernel resources. Use resource-limited Docker for load/fault work. No live production chaos, network scanning or restore facility is supplied.
- Adapters trust reviewed test assertions. A malicious or incorrect runner can lie in a valid result file. Independent failing controls and test review are essential. Tool-output instructions are never executed by the engine; the host model must preserve that distinction too.
- Runner suites are the affected-run unit. Selecting one case can run its entire suite; the report lists those results. No automatic dependency/change-impact graph is claimed.
- Configuration changes prevent automatic “resolved” claims in comparisons. Disappearing static findings and omitted scenarios remain unverified. A same-name assertion altered to hide a bug is still a bad test; compare implementation changes during review.
- Only one active audit per engine instance is allowed. Separate processes are not coordinated. Hard termination can leave temporary resources. Reports are local, mutable files, not signed audit logs or a remote service.
- Host-specific recipes are documented but untested unless the compatibility matrix explicitly says otherwise. No promise of universal host support, OWASP certification, trademark availability, legal compliance or future incident prevention is made.

Useful next contributions: precise semantic inventory adapters, scanner/browser images with pinned acceptance fixtures, versioned provider-contract fixtures, fingerprint-bound human triage, native isolated runners, and validated client-version records. These are future work, not current capabilities.
